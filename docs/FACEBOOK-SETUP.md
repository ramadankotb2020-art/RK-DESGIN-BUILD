# Facebook — إعداد اختياري آمن

## ما الذي تم بناؤه؟
`info.txt + images → npm run build → project HTML + social-posts.json → GitHub Actions → Meta Graph API`

النشر مغلق افتراضيًا. المشاريع القديمة لا تنشر دفعة واحدة؛ كل مشروع يحتاج `فيسبوك: نعم`. المشروع المنشور يولد له نص يتضمن العنوان والوصف والتصنيف ورابطه وCTA. يتم إرسال منشور رابط إلى `/PAGE_ID/feed`؛ صورة بطاقة الرابط تأتي من Open Graph الخاص بغلاف المشروع، وليس رفع صورة مستقلة أو فيديو إلى Facebook. شكل البطاقة النهائي وتحديث كاشها يخضعان لـ Meta، ويجب اختباره على الصفحة الحقيقية.

اخترنا Actions بدل إضافة Backend أو قاعدة بيانات مدفوعة، لأن المصدر GitHub أصلًا والتحديثات غير لحظية. GitHub يتيح standard hosted runners مجانًا للمستودعات العامة، بينما الخاصة لها حصص وشروط استخدام حسب الخطة. لا تفعل larger runners أو ميزانية مدفوعة بلا حاجة. راجع حدود حسابك الحالية. [3](https://help.github.com/en/github/setting-up-and-managing-billing-and-payments-on-github/about-billing-for-github-actions)

موقع العرض يظل ملفات ثابتة على Cloudflare. وفق الوثائق الرسمية لخطة Pages المجانية: 500 بناء شهريًا، 20,000 ملف، وحد الملف الواحد 25 MiB. Functions تحسب ضمن حصص Workers؛ لهذا لم نستخدم Function لكل زيارة أو صفحة مشروع. راجع الحدود قبل التفعيل: https://developers.cloudflare.com/pages/platform/limits/

## إعداد Meta بواسطة صاحب الصفحة
1. أنشئ/استخدم تطبيق Meta مناسبًا لاستخدام Pages API واربط حسابًا يملك مهام إنشاء محتوى للصفحة.
2. اتبع دليل Meta الحالي للحصول على Page Access Token، وليس App Token أو رمز مستخدم غير مناسب. دليل المنشورات يذكر الصلاحيات `pages_manage_engagement`, `pages_manage_posts`, `pages_read_engagement`, `pages_read_user_engagement` حسب العملية؛ اكتشاف الصفحات يمكن أن يحتاج `pages_show_list`. صلاحيات App Review / Advanced Access والتحقق التجاري تعتمد على نمط التطبيق والمستخدمين. لا يفترض الكود أن الصلاحيات تُمنح تلقائيًا.
3. اختبر صلاحيات حسابك وتطبيقك حسب دليل Meta، وراجع صلاحية التوكن ودورة تجديده. لا تفترض أنه صالح للأبد.
4. اضبط إصدار API مدعومًا من لوحة Meta؛ مثال الوثيقة وقت المراجعة `v26.0`. الإصدار متغير إعداد إلزامي وليس مخفيًا في الواجهة.

المرجع الرسمي للمتطلبات ونشر منشورات الروابط: https://developers.facebook.com/documentation/pages-api/posts

**لا ترسل التوكن في المحادثة، ولا تضعه في JavaScript أو info.txt أو Git.** App Secret غير مطلوب لهذا التنفيذ. إذا تطلب إعداد تطبيقك appsecret_proof فهذه إضافة لاحقة في الخادم/Action، وليست سببًا لإظهار App Secret في الواجهة.

## إعداد GitHub

**خطوة لازمة قبل التفعيل:** انسخ `docs/workflow-templates/facebook.yml.template` إلى `.github/workflows/facebook.yml` باستخدام حسابك في GitHub. اتصال Arena الحالي لا يملك صلاحية كتابة workflows؛ لذلك القالب جاهز لكن الـworkflow نفسه غير مثبت. يمكن كذلك نسخ `quality.yml.template` إلى `.github/workflows/quality.yml` لتفعيل اختبارات CI الاختيارية. هذه الملفات لا تتطلب وضع أي توكن داخلها.

Settings → Secrets and variables → Actions:

Secret:
- `FACEBOOK_PAGE_TOKEN`: التوكن الخاص بصفحتك.

Variables:
- `FACEBOOK_ENABLED`: ابدأ بـ `false`، ثم `true` عند جاهزية الحساب.
- `FACEBOOK_PAGE_ID`: رقم الصفحة الحقيقي.
- `FACEBOOK_API_VERSION`: الإصدار المدعوم مثل `v26.0` بعد التحقق من Meta.

فعّل Issues في المستودع، واسمح للـworkflow بـ `issues: write`. يستخدم `GITHUB_TOKEN` التلقائي؛ لا يحتاج PAT من المستخدم. لا تحذف Issues الخاصة بسجل النشر أو تغير عناوينها.

الـworkflow يعمل فقط على فرع GitHub الافتراضي وبعد التفعيل؛ لا يعمل من Pull Requests ولا Preview branches. يجب أن يكون هذا هو نفس فرع إنتاج Cloudflare؛ إن لم يكن كذلك راجع شرط الفرع قبل التفعيل. لا تستخدم pull_request_target مع أسرار النشر.

## أول تجربة
1. اختَر مشروعًا واحدًا منشورًا، واكتب وصفًا حقيقيًا و`فيسبوك: نعم` في info.txt.
2. شغّل البناء محليًا وراجع نص `social-posts.json` والغلاف ورابط المشروع.
3. ارفع التغييرات وانتظر نشر Cloudflare. الـworkflow ينتظر إتاحة بيانات المشروع حتى نحو 4 دقائق قبل الحجز؛ إذا تأخر النشر يفشل بأمان ويمكن إعادة تشغيله بعد اكتمال النشر.
4. فعّل المتغير وشغّل **Optional Facebook project publishing** من Actions يدويًا أول مرة. التشغيلات التالية تبدأ مع تغييرات فولدرات المشاريع على فرع الإنتاج.
5. راجع منشور Facebook الحقيقي وصورة الرابط. استخدم Sharing Debugger لإعادة قراءة OG عند الحاجة؛ لا تكرر إرسال المشروع لحل مشكلة الكاش.

## منع التكرار وحالات المزامنة
ينشئ التنفيذ Issue دائمًا عنوانه `[RK Facebook] <project-id>` **قبل** إرسال أي طلب إلى Meta:
- `publishing`: تم حجز المشروع؛ الطلب قد يكون جاريًا أو يحتاج مراجعة.
- `facebook_posted`: نجح الإرسال وتم حفظ postId ووقت النشر، ثم أُغلق الـIssue.
- وجود السجل مفتوحًا أو مغلقًا يمنع أي إرسال آلي جديد لنفس المعرف.
- workflow concurrency يمنع التشغيل المتزامن من Actions؛ لا تشغّل نسخًا يدوية مستقلة بالتوازي.
- عند Timeout أو فشل تسجيل نتيجة بعد نجاح Meta المحتمل، يبقى الحجز. افحص الصفحة يدويًا قبل إعادة المحاولة. هذا تصميم محافظ يمنع التكرار على حساب الحاجة إلى تدخل بشري؛ لا ندعي exactly-once على شبكة خارجية.
- لإعادة محاولة فشل مؤكد: تحقق أولًا من عدم وجود منشور، ثم قرر مع المطور إعادة فتح المسار بإزالة الحجز/أرشفته بعد توثيق القرار. إغلاق Issue وحده لا يسمح بإعادة الإرسال.
- تعديل مشروع منشور لا يعدل منشور Facebook القديم تلقائيًا، وإلغاء نشر صفحة الموقع لا يحذف منشور Facebook.

## الاختبارات المنفذة
أربع حالات محلية Mock: الإغلاق الافتراضي بلا شبكة، تخطي مشروع مسجل، الحجز قبل الإرسال وحفظ النجاح، وفشل غامض بدون إعادة إرسال. لم نستخدم توكنًا حقيقيًا ولم ننشر شيئًا. اختبار Meta الحقيقي يحتاج إعداد صاحب الصفحة.
